# Project idea

## The problem

- In a production application, a lot of requests
  - Trace storage becomes a cost factor
- What to trace becomes an important question
- Existing methods:
  - Random sampling (store 1% of traces)
  - Anomalies (store only if duration > 1s)
- Without application specific context, observability is limited

## The project

- Build a small mock microservice application
  - Multiple components: DB, cloud storage, processing, LLM
  - Injectable faults and delays
- Try multiple different versions of a trace reducer
  - Naive
  - Sampling
  - Anomalies + sampling
  - Statistical sampling (keep traces in proportion to how unusual they are versus a history of error rates and latencies)
  - LLM agent
  - Increasing trace resolution when an anomaly happens
  - Logic in collector vs. application
  - Combinations
- Increase traces/s and see how each holds up

## The output

- Seeing how each method of trace reduction responds to increasing number of traces (i.e. application complexity)
- Do simple reducers miss rare exceptions?
- Does a smarter reducer matter enough for finding exceptions and anomalies?
- Can an LLM keep up with reasonable costs?
- Application level vs. collector level adaptability?

## Current status

Done:

- Mock application (`mock-io`): Dagster jobs replay YAML scenarios (DB, cloud storage, HTTP and service calls) and emit OpenTelemetry spans per service
  - `supermarket` scenario: 49 jobs over many services, generated by `scripts/generate_supermarket.py`
  - Injectable delays and failures, plus named anomalies (slow services, outage windows, flapping HTTP, huge blobs)
  - Low background error rate, so errors and anomalies are the exception rather than the norm
- Reproducible workloads: outcomes are fixed by a seed (`--seed`, also in the API and `mock-io-ctl`); trace IDs and timings still differ per run
- Ground truth: every injected anomaly is logged per trace (`MOCK_IO_GROUND_TRUTH_FILE`)
- Load generation: Poisson arrivals (`--rate/--runs/--workers`); runs overlap, and jobs within a run execute in parallel (multiprocess executor)
- Trace reducers as OpenTelemetry Collector configs, all run side by side in one collector on the same workload:
  - Naive (`baseline_naive`): keeps everything, the reference
  - Sampling (`sampling`): 10% probabilistic
  - Anomalies + sampling (`anomalies_sampling`): tail sampling on errors, latency > 1 s, or 5% random
  - Memory pressure (`anomalies_sampling_limited`): the same with at most 30 traces held at once; the oldest are dropped without a decision
  - Optional forwarding to Jaeger for browsing
- Evaluation (`mock-io-eval`): traces/spans/bytes kept, trace completeness, recall for anomalous, error, slow and normal traces and per anomaly label, precision; a recall matrix across all methods
- `scripts/check_parallelism.py` checks a capture for overlapping runs, jobs and calls
- Benchmark load generators that skip the app (which Dagster limits to a few runs/s):
  - `mock-io-replay`: resends a recorded capture at any rate with fresh IDs and matching ground truth, so recall can be measured versus traces/s
  - telemetrygen: synthetic traces for raw collector throughput

  - Stateless collectors (naive, probabilistic sampling) stay flat at about 100–140 MB regardless of rate
  - Tail sampling memory grows with rate × `decision_wait` (about 2 MB per held trace): 290 → 647 MB from 2 to 5/s, then killed at the 1 GB limit at 10/s (after exporting 81% of traces) and at 20/s before its first decision (nothing kept, later requests refused)
  - A trace cap (`num_traces: 30`) avoids OOM but silently drops the oldest traces: kept share falls as 1/rate, and recall drops with it, regardless of whether the trace was anomalous
  - Failure mode of a smart reducer under load is total (OOM: lose everything), versus degraded (cap: lose most) or none (blind sampling)
- **Decision: whole-trace tail sampling in the collector is a dead end for now.** Its memory is rate × `decision_wait` × trace size, our traces are large (about 900 spans) and long (production jobs can take 10 minutes, so the wait would be minutes), and an OOM loses everything. Instead, approaches that hold less or nothing (implemented, not yet measured):
  - Calibration (`scripts/calibrate_thresholds.py`): per (service, span name) latency thresholds of 5× the median from a baseline capture, plus per-job run statistics; generates the two collector configs below and the thresholds the app reducers use. Calibrate on a different seed than the evaluation run
  - Statistical span filter (`span_filter`): stateless collector filter that drops detail spans faster than their threshold unless they errored; keeps the skeleton (run/job/op spans) and 1% of whole traces. No per-trace memory
  - Per-job hold time (`routed_tail_sampling`): the app tags every span with `mock_io.run_job`, a `routing` connector sends each job's spans to a tail sampler whose `decision_wait` fits that job's longest run (45/60/90 s buckets for supermarket, instead of 120 s for all), with a per-job latency threshold (1.5× the job's median run). Answers "a different hold duration per job"; still tail sampling, so memory still grows with rate, but by the job's own duration
  - App-side job buffering (`job_buffer`): the app holds a job's spans in its own process until the job's root span ends (no guessing a wait), then sends all of them if anything errored or was slow, or 5% by trace ID. Memory is bounded by the running jobs and spread over the job processes
  - App-side adaptive resolution (`resolution`): no buffering. Always sends the skeleton, plus failed or slow detail spans and the path up to them
  - App-side reducers run in shadow next to the full export, each to its own collector (`app_job_buffer`, `app_resolution`), so one workload scores everything. The replay benchmark cannot measure them (it bypasses the app)
  - New metric: evidence, the share of anomalous traces with at least one injected span kept. Span-level methods keep every trace's skeleton, so trace recall is about 100% for them by construction
  - Offline estimate on the calibration capture itself (in-sample, so optimistic): `span_filter` and `resolution` keep about 14% of spans, `job_buffer` about 30% of spans (55% of traces); all keep evidence of 100% of anomalous traces

- Done (see RESULTS.md runs 2 and 3, seeds 7 and 8, thresholds calibrated on seed 42): `span_filter` and `app_resolution` keep about 15% of spans with 100% evidence, `app_job_buffer` keeps 29-41% of spans with 100% evidence, `routed_tail_sampling` keeps only 47% evidence. The routed shortfall is not a routing or flush problem: whole-trace duration barely separates anomalous from normal traces (anomalous traces median 78% of the job threshold, normal 70%), so the collector's trace-level latency policy cannot select them without keeping most normal traces. ## Notes/ideas

- per component tracing parameters
- - consider how we could achieve a different "hold duration" for traces per job? (done: `routed_tail_sampling`, and `job_buffer` holds exactly until the job ends)
- agent for configuration
- time based differences in sampling
- different faults (latency, full errors) (done: latency multiplier/add, failures, payload size, iteration windows)
- different faults per component? (done: per call group and per service, e.g. `slow_tax_service`, `huge_blob`)
- statistical sampling: per-key (service/operation) history of error rate and latency percentiles
  - history store: in-memory counters on the hot path, periodically persisted or refreshed from a DB (SQLite/Redis); a per-trace DB lookup may not keep up at high rates
  - cold start: keep everything for the first N traces, seed from a prior seeded run, or decay toward a prior
  - drift: sliding window or EWMA, so a sustained outage does not become the new normal (test with the `email_outage` / `http_flap` windows)
  - needs custom code (no stock collector policy): a small service beside the collector or a custom processor
  - evaluation: train the history on a separate seeded run; compare a learning-during-run variant with a pre-trained one
- make anomaly rates tunable (about 1% or less) so "do simple reducers miss rare exceptions?" is meaningful
- track resource usage of different collectors
